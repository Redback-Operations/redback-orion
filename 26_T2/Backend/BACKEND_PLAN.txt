TEAM ROLE
---------
The backend team is responsible for building and maintaining the API Gateway
that connects the frontend to the Player Tracking and Crowd Monitoring services.

The backend does NOT build the ML models. These are owned by the Player and
Crowd teams. The backend is responsible for integrating these services,
managing processing jobs, storing results, handling authentication, and
providing APIs that allow the frontend to access the results.

The backend acts as the central communication layer between the frontend,
processing services and database.

Each uploaded video creates a unique job_id. Player Tracking and Crowd
Monitoring results are stored against this job so that the frontend can
retrieve results for the correct uploaded video.

During development, services can run locally on separate ports and communicate
over HTTP. Docker Compose is also available to run the project services
together.

API ENDPOINTS (Gateway)
-----------------------

Auth:
  POST /auth/register       — create a new user account
  POST /auth/login          — authenticate user
  POST /auth/refresh        — refresh authentication tokens
  POST /auth/logout         — revoke refresh token and log out
  GET  /auth/me             — return current logged-in user information

Video Processing:
  POST /upload
       — accepts a video and creates a processing job
       — returns a unique job_id for tracking the uploaded video

Job Management:
  GET  /status/{job_id}
       — returns processing status and available job information

  GET  /jobs?page=1&limit=10
       — returns paginated jobs available to the logged-in user

  GET  /jobs/{job_id}
       — returns full information for a specific job

  POST /jobs/{job_id}/retry
       — retries eligible failed processing

  POST /jobs/{job_id}/recover
       — supports recovery of interrupted or failed jobs

  GET  /jobs/{job_id}/heatmap
       — returns the Crowd Monitoring heatmap for a job

  DELETE /jobs/{job_id}
       — deletes a job and its results when the user has permission

Processing Services:
  POST /players
       — sends video data to the Player Tracking service

  POST /crowd
       — sends video data to the Crowd Monitoring service

Result APIs:
  GET /analysis/{job_id}
       — returns Analysis results for the requested job

  GET /analytics/{job_id}
       — returns summarised Player Tracking and Crowd Monitoring analytics
         for the requested job

  GET /player-tracking/{job_id}
       — returns formatted Player Tracking results for the requested job

  GET /crowd/{job_id}
       — returns Crowd Monitoring results for the requested job

System:
  GET /
       — confirms that the backend is running

  GET /health
       — checks backend and processing-service health

  GET /test
       — basic backend API test

Using job_id for the result APIs ensures that results belong to the selected
uploaded video rather than relying on the latest processed job.

STORAGE STRATEGY
----------------
Local Development:
  - Uploaded videos are stored in the configured upload location.
  - Job information and processing results are stored in PostgreSQL.
  - Player Tracking and Crowd Monitoring results are associated with job_id.

Docker:
  - Services use Docker volumes where shared file access is required.
  - PostgreSQL provides persistent job and result storage.
  - Docker service names are used for communication between containers.

The job_id remains the main link between an uploaded video, its processing
state and its results.


DATABASE SCHEMA (PostgreSQL)
-----------------------------

Table: users
  user_id       UUID        PRIMARY KEY
  email         VARCHAR     UNIQUE, NOT NULL
  username      VARCHAR     UNIQUE, NOT NULL
  password      VARCHAR     hashed password
  role          VARCHAR     user role
  created_at    TIMESTAMP   account creation time

Table: jobs
  job_id          UUID        PRIMARY KEY
  user_id         UUID        FOREIGN KEY → users.user_id
  status          VARCHAR     current processing status
  video_path      VARCHAR     uploaded video location
  player_result   JSONB       Player Tracking result
  crowd_result    JSONB       Crowd Monitoring result
  error           VARCHAR     processing error information
  retry_count     INTEGER     processing retry count
  progress        INTEGER     processing progress
  started_at      TIMESTAMP   processing start time
  completed_at    TIMESTAMP   processing completion time
  failure_reason  VARCHAR     processing failure information
  created_at      TIMESTAMP   job creation time
  updated_at      TIMESTAMP   last update time

Table: refresh_tokens
  - stores refresh-token information associated with users
  - supports authentication token renewal and logout/revocation

Player Tracking and Crowd Monitoring results are stored against the same job,
allowing result APIs to retrieve information using job_id.


AUTHENTICATION
--------------
- Users can register and log in through the backend.
- Passwords are hashed rather than stored as plain text.
- Authentication uses access and refresh tokens.
- Protected endpoints require a valid access token.
- Refresh tokens allow users to obtain a new authentication token pair.
- Logout revokes the refresh token.
- User roles are used for access control.

Auth Endpoints:
  POST /auth/register
  POST /auth/login
  POST /auth/refresh
  POST /auth/logout
  GET  /auth/me

ROLE-BASED ACCESS CONTROL (RBAC)
---------------------------------
The backend uses roles to control access to protected functionality.

Authentication and authorisation logic determines whether the current user can
access the requested resource.

Job ownership is also checked so that users cannot access another user's
processing jobs unless their role provides the required permission.

Role information is stored with the user and is used by backend authentication
dependencies when protected routes are accessed.


BACKGROUND PROCESSING
---------------------
Video processing can take significantly longer than a normal API request, so
the backend manages processing through jobs.

General processing flow:

  1. POST /upload receives the video.
  2. Backend validates the uploaded video.
  3. A new job is created in PostgreSQL.
  4. A unique job_id is returned.
  5. Player Tracking and Crowd Monitoring processing takes place.
  6. Job status and progress are updated.
  7. Results are stored against the job.
  8. The frontend checks processing status using job_id.
  9. Completed results can be retrieved using the job-specific result APIs.

This prevents the frontend from having to wait for the complete ML processing
operation before receiving a response from the initial upload request.


ERROR HANDLING STRATEGY
-----------------------
The backend handles processing failures at both service and job level.

The implementation includes:

  - Player Tracking and Crowd Monitoring timeout handling
  - processing failure information
  - partial-result handling
  - retry handling
  - job recovery
  - job-health checking
  - stuck-job detection
  - upload validation
  - video-format validation

Successful processing results are preserved where possible rather than being
discarded because another part of processing failed.

Failure information is stored with the job so that it can be reported to the
frontend and used by retry or recovery functionality.

CONTRACT DEFINITIONS
--------------------

CONTRACT 1 — Backend Gateway → Frontend
  The backend exposes authenticated APIs for uploads, jobs, Analysis,
  Analytics, Player Tracking and Crowd Monitoring.

  FastAPI interactive documentation:
    http://localhost:8000/docs

  The frontend stores the job_id returned from an upload and uses this ID when
  checking processing status and retrieving results.


CONTRACT 2 — Backend Gateway → Player Tracking Service
  The Player Tracking integration uses the confirmed Player service rather
  than the earlier placeholder/mock-only contract.

  The backend sends the required video for Player Tracking processing.

  The returned Player Tracking information is stored in player_result against
  the corresponding job.

  result_formatter is used where required to convert the processing result
  into the structure exposed through the backend API.


CONTRACT 3 — Backend Gateway → Crowd Monitoring Service
  The Crowd Monitoring integration uses the confirmed Crowd service.

  Crowd processing endpoint:
    POST /process-crowd-detection

  The backend provides the video information required by the Crowd service.

  Crowd results can include:
    - summary
    - peak crowd information
    - heatmap
    - anomaly information
    - time-series information
    - density information

  The returned Crowd result is stored in crowd_result against the corresponding
  job.
