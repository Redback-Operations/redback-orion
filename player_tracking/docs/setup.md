# Player Tracking setup

Run every command from `player_tracking/` unless a step says otherwise.

## Folder layout

```
player_tracking/
├── analysis_pipeline/            Runs a match video through tracking (and later analytics)
│   ├── detect_and_track.py       YOLO + ByteTrack → annotated video + tracks CSV
│   └── configs/                  tracker settings (afl_broadcast_bytetrack.yaml)
├── player_service/               The web API the backend calls (port 8001)
├── Orion_Player_Tracking_Studio/ Desktop app for reviewing and correcting tracking results
├── training/                     Datasets, labelling and model training
├── evaluation/                   Tracking quality checks
├── experiments/                  Ball tracking, Forward-50, jumper numbers: not in the pipeline yet
├── player_tracking_logic/        T1 code that player_service still runs (moving into analysis_pipeline/)
├── docs/                         This folder
├── requirements.txt              For training/, evaluation/ and experiments/
│
│   Local only (git-ignored):
├── models/                       Model weights, from training/download_models.py
├── data/                         raw/ labelled datasets, videos/ match footage
├── datasets/                     Train/val splits built by training/build_datasets.py
├── outputs/                      Tracking results: annotated videos, tracks CSVs
└── runs/                         Training runs
```

Class indices differ between the raw datasets, so any conversion or merge script must use a per-dataset mapping. See `datasets.md`.

## 1. Python environments

Python 3.11 and [uv](https://docs.astral.sh/uv/) are the team standard.

For the service and the analysis pipeline:

```bash
cd player_service
uv venv .venv --python 3.11
source .venv/bin/activate          # Windows: .venv\Scripts\activate
uv pip install -r requirements.txt
cd ..
```

For training, evaluation and experiments (a separate environment, because it adds training-only packages):

```bash
uv venv .venv --python 3.11
source .venv/bin/activate
uv pip install -r requirements.txt
```

If you have an NVIDIA GPU, install the matching PyTorch build first: https://pytorch.org/get-started/locally/

## 2. Model weights

Weights aren't stored in git. They're attached to the `models-v1` GitHub release:
https://github.com/Redback-Operations/redback-orion/releases/tag/models-v1

```bash
python training/download_models.py                     # all three
python training/download_models.py player_ref_best.pt  # just the default model
```

Each file is checked against a SHA-256 checksum. The script needs only the Python standard library, so it runs in either environment. `player_service` also downloads `player_ref_best.pt` by itself the first time it starts, if the file is missing.

| File | Classes | Use it for |
|---|---|---|
| `player_ref_best.pt` | PLAYER, REF | Default. Works on any match. |
| `all_teams_best.pt` | CAR, GCS, HAW, CAT, REF, SS, WB | Matches between those teams only |
| `all_classes_best.pt` | the 7 teams plus BALL, POST | Experiments |

## 3. Data and match footage

Labelled datasets and match videos are too large for git and include broadcast footage, so they stay in the shared Drive folder **afl_player_tracking**:
https://drive.google.com/drive/u/0/folders/1Pioq0m2zHVQiwKFOBVWZUQ6PtYcP01Ui

```bash
python training/download_data.py data       # raw datasets + match videos (about 16 GB)
python training/download_data.py datasets   # built train/val splits
```

The match videos are about 5 GB each. Google Drive blocks a file for roughly 24 hours after it's been downloaded too often. If that happens, the script stops with a message saying so. Download that file in a browser, or try again the next day.

For a first test run, cut a short clip from one match instead of tracking the whole thing:

```bash
ffmpeg -ss 1200 -i data/videos/broadcast_essendon_hawthorn.mp4 -t 20 -c copy data/videos/test_clip_20s.mp4
```

## 4. Check it works

```bash
python analysis_pipeline/detect_and_track.py data/videos/test_clip_20s.mp4
```

The annotated video and the tracks CSV are written to `outputs/`.

To test the service, start it and open http://localhost:8001/docs:

```bash
cd player_service
source .venv/bin/activate
uvicorn main:app --port 8001
```

## Conventions

- `data/raw/` holds training data only (image and label pairs). No videos, no outputs.
- `data/videos/` holds match footage, named to match its dataset folder (`gcs_vs_car.mp4` → `data/raw/gcs_vs_car/`).
- `outputs/` holds anything generated by tracking. Never copy outputs back into `data/`.
- After building a new dataset, upload it to the matching Drive folder. A new model gets a new GitHub release (`models-v2`, …) and its checksum goes in `training/download_models.py`.
